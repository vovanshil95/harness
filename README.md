# harness

Telegram-бот на базе [Hermes Agent](https://github.com/NousResearch/hermes-agent) в Docker.
Работает как gateway: принимает сообщения в Telegram и отвечает через DeepSeek.

## Запуск

```bash
cp .env.example .env      # подставить реальные токены
docker compose up -d
docker logs -f hx-hermes-v2
```

## Команды

| действие | команда |
|---|---|
| запуск | `docker compose up -d` |
| статус | `docker compose ps` |
| логи | `docker logs -f hx-hermes-v2` |
| перезапуск | `docker compose restart hermes` |
| остановка | `docker compose down` |
| **после правки `.env`** | `docker compose up -d --force-recreate hermes` |

## Выбор модели и провайдера

Настроены два провайдера, ключи обоих лежат в `.env` одновременно — переключение
не требует их менять.

```bash
./switch-model.sh deepseek           # deepseek-v4-pro
./switch-model.sh kimi               # kimi-k3
./switch-model.sh kimi kimi-k2.6     # конкретная модель
./switch-model.sh status             # что активно сейчас и какие ключи видны
```

| провайдер | модели | ключ в `.env` |
|---|---|---|
| `deepseek` | `deepseek-v4-pro`, `deepseek-v4-flash` | `DEEPSEEK_API_KEY` |
| `kimi` | `kimi-k3` (1M контекст), `kimi-k2.7-code`, `kimi-k2.7-code-highspeed`, `kimi-k2.6` | `KIMI_API_KEY` |

Для Kimi обязателен `KIMI_BASE_URL=https://api.moonshot.ai/v1`: по умолчанию hermes
идёт на `api.moonshot.cn`, а китайский эндпоинт доступен не отовсюду.

Под капотом скрипт делает три `hermes config set` и `restart`. Вручную то же самое:

```yaml
# hermes-data/config.yaml — перекрывает переменные окружения
model:
  default: deepseek-v4-pro
  provider: deepseek
  base_url: https://api.deepseek.com/v1
```

Имя переменной с ключом должно соответствовать провайдеру: при `provider: deepseek`
читается `DEEPSEEK_API_KEY`, при `provider: kimi` — `KIMI_API_KEY`. Файл принадлежит
uid 10000, правится через `sudo`. `config.yaml` перечитывается при каждом старте,
так что достаточно `restart`.

Все модели обоих провайдеров — **reasoning**: часть токенов уходит на размышление
до ответа. При маленьком `max_tokens` ответ придёт пустым с `finish_reason: length`.

## Особенности конфигурации

Каждый пункт ниже — следствие конкретной поломки, а не стилистический выбор.

**`command: gateway run`**
Без аргументов контейнер запускает интерактивный TUI. TTY в фоне нет, stdin сразу
отдаёт EOF, агент считает это концом ввода и завершается с кодом 0 — и `restart`
поднимает его заново по кругу.

**`extra_hosts: api.telegram.org:149.154.167.220`**
DNS отдаёт для `api.telegram.org` адрес `149.154.166.110`, который с некоторых
хостов не отвечает (таймаут ~12 с). Живой адрес того же Bot API — `149.154.167.220`,
отвечает за 0.2 с. Без этой строки Telegram-адаптер уходит в перебор резервных
адресов через DNS-over-HTTPS и генерирует ~900 соединений в секунду.

Адрес прибит статически. Если он перестанет отвечать — подобрать другой из
диапазона `149.154.160.0/20` либо поднять прокси.

**`./hermes-data:/opt/data`**
В образе `HERMES_HOME=/opt/data`. Монтирование в `/root/.hermes` не работает:
агент туда ничего не пишет, и данные не переживают пересоздание контейнера.

**`mem_limit` / `pids_limit`**
Не оптимизация, а страховка. При сетевых сбоях агент уходит в шторм переподключений;
без лимитов это выедает память всей машины и приводит к global OOM — вплоть до
потери SSH. С лимитами процесс упирается в свой cgroup и умирает один.

**`restart: on-failure:3`**
Не `unless-stopped`: при циклическом падении docker сдаётся после трёх попыток,
а не крутит бесконечный цикл.

## WebDAV для Obsidian

Синхронизация хранилища Obsidian через плагин **Remotely Save**.

Настройки плагина (Settings → Remotely Save → Remote Service → WebDAV):

| поле | значение |
|---|---|
| Server Address | `https://5-8-9-221.sslip.io/webdav` |
| Username | из `WEBDAV_USERNAME` |
| Password | из `WEBDAV_PASSWORD` |
| Auth Type | Basic |
| Depth Header | `depth_1` |

### Карта путей

Один и тот же каталог виден по-разному в разных местах — это частый источник
путаницы, особенно если спрашивать про путь у самого агента:

| откуда смотрим | путь |
|---|---|
| файловая система сервера | `~/harness/webdav-data/me/` |
| контейнер `hx-webdav` | `/data/me/` |
| контейнер `hx-hermes-v2` | `/opt/data/vault/` |
| по сети (WebDAV) | `https://5-8-9-221.sslip.io/webdav/me/` |
| Remotely Save (Server Address) | `https://5-8-9-221.sslip.io/webdav` (без `/me`) |

Хранилище примонтировано и в hermes — так агент может читать и править заметки,
а изменения подхватит Obsidian при следующей синхронизации. Монтируется внутрь
`/opt/data`, потому что у образа `HERMES_WRITE_SAFE_ROOT=/opt/data` и вне этого
пути агент писать отказывается. Чтобы дать доступ только на чтение — добавить
`:ro` к строке тома в `docker-compose.yml`.

Файлы лежат в `webdav-data/` рядом с compose — обычные каталоги, забрать можно
простым `scp` или `rsync`, без выгрузки через плагин.

### Про имя `5-8-9-221.sslip.io`

Домена у сервера нет, а сертификат на голый IP публичные CA не выдают.
`sslip.io` — публичный резолвер, который любое имя вида `1-2-3-4.sslip.io`
превращает в соответствующий адрес. Никаких DNS-записей заводить не нужно, но
имя настоящее, поэтому Let's Encrypt выдаёт на него обычный доверенный
сертификат — работает и в мобильном Obsidian.

Зависимость от стороннего сервиса тут только в резолвинге имени. Если `sslip.io`
станет недоступен — завести свою A-запись на `5.8.9.221` и поменять домен в
Caddyfile, всё остальное останется как есть.

### Аутентификация

WebDAV выведен в caddy **мимо** oauth2-proxy, которым закрыт остальной
`remote.unicort.ru`: Remotely Save умеет только basic auth и не проходит
OAuth-редиректы. Доступ защищён логином и паролем самого WebDAV поверх TLS.

## Несколько пользователей

Сейчас активен один пользователь. Схема на одного: бот `hx-hermes-v2`, LiveSync
`hx-livesync` (база `obsidian`), WebDAV `hx-webdav` как запасной канал.

Имя контейнера агента — `hx-hermes-v2`, а не `hx-hermes`: старое имя удерживает
зависший контейнер, который docker отказывается отдавать. Любая команда
`docker inspect` или `docker stats` по нему блокируется, поэтому в скриптах и
командах используется имя с суффиксом.

Добавление нового пользователя — `./add-user.sh <nick>` (синхронизация + URI +
passphrase), плюс вручную: свой контейнер агента с новым бот-токеном и свой волт.
См. «Добавление пользователя (одной командой)».

**Почему на каждого — отдельный бот, а не один.** Telegram позволяет опрашивать
токен только одному процессу: второй получает `409 Conflict: terminated by other
getUpdates request`. Документация Hermes подтверждает — «the same token cannot be
polled by two profiles at once». Вебхуки не спасают: адаптер работает только
опросом и при старте сам вызывает `delete_webhook`.

**Почему на каждого — отдельный контейнер, а не профиль.** Профили Hermes
(`multiplex_profiles`) разделяют конфиг, память и сессии, но не файловую систему —
изоляция рабочих каталогов пока лишь
[запрошенная функция](https://github.com/NousResearch/hermes-agent/issues/9514).
Отдельные контейнеры дают гарантию через монтирование: чужой каталог физически
не подключён.

**Чего это не даёт.** Владелец сервера имеет root и прочитает любой каталог через
SSH в обход схемы. Изоляция защищает от ошибок агента, а не от администратора машины.

## Синхронизация Obsidian (LiveSync)

Волт синхронизируется через **Self-hosted LiveSync**: устройства реплицируются
с CouchDB. На сервере за каждого пользователя отвечает контейнер
**`livesync-cli`** — headless-версия движка LiveSync (без Electron и Xvfb),
который раскладывает волт обычными `.md` на диск, чтобы Hermes читал файлы
напрямую.

```
телефон ──┐
          ├──► CouchDB ◄──► livesync-cli (headless) ──► ./vault-<nick> ──► Hermes
ноут   ───┘
```

| сервис | что делает |
|---|---|
| `couchdb` | хранилище репликации, `https://couchdb.5-8-9-221.sslip.io` |
| `livesync-cli` | headless-клиент LiveSync, материализует волт в `./vault-<nick>` |

Один пользователь = одна база CouchDB + один контейнер `hx-livesync-<nick>` +
один волт `vault-<nick>`. E2E-шифрование у каждого своё (свой passphrase), базы
физически разделены, волт монтируется только в нужного Hermes.

Раньше серверным клиентом был контейнер `obsidian` (Electron+Xvfb, ~2 ГБ RAM).
Он заменён на `livesync-cli` (~сотни МБ) — тот же протокол LiveSync, но без
графической оболочки.

### Почему не WebDAV

`webdav` остаётся как запасной путь и хранит копию волта. LiveSync передаёт
изменённые блоки, а не файлы целиком, разрешает конфликты по дереву ревизий
и доставляет правки за секунды через `_changes?feed=continuous` — открытый
HTTP-запрос, в который сервер дописывает события.

## Добавление пользователя (одной командой)

Нового пользователя LiveSync добавляет скрипт `add-user.sh`. Вход — английский
nick, выход — passphrase и setup-URI, которые отдаются пользователю.

```bash
cd ~/repos/harness
./add-user.sh alice
```

Скрипт делает всё сам:

1. генерирует случайный passphrase (E2E-шифрование волта);
2. на сервере создаёт базу `obsidian-<nick>`, волт `vault-<nick>`, каталог
   данных `livesync-<nick>-data` и контейнер `hx-livesync-<nick>` (uid 1000,
   лимиты 512 МБ / 1 CPU);
3. локально генерирует setup-URI и кладёт его в буфер обмена (резерв —
   `users/<nick>.txt`).

Пользователю отдаётся **URI + passphrase**. В Obsidian он выбирает
*Setup wizard → Use setup URI*, вставляет строку и вводит passphrase — больше
ничего настраивать не нужно (E2E, база, папка подключены автоматически).

Требования:

- образ `livesync-cli` должен быть собран на сервере (см. сборку ниже);
- библиотека для генерации URI стоит в `tools/node_modules` (один раз
  `cd tools && npm ci`).

Каталоги `tools/node_modules/` и `users/` в git не попадают: в них секреты и
сборочный мусор.

### Сборка образа `livesync-cli`

Образа на Docker Hub нет, собирается из исходников
([obsidian-livesync](https://github.com/vrtmrz/obsidian-livesync)):

```bash
git clone --depth 1 https://github.com/vrtmrz/obsidian-livesync.git /tmp/ls
cd /tmp/ls && docker build -f src/apps/cli/Dockerfile -t livesync-cli .
```

## Деплой

CI нет, выкладка ручная. В репозитории только конфигурация: `.env` и все
каталоги с данными в него не попадают, их место — на сервере.

```bash
scp docker-compose.yml switch-model.sh <сервер>:~/harness/
ssh <сервер> 'cd ~/harness && docker compose up -d <сервис>'
```

Перед правкой конфигурации на сервере рядом кладётся копия
`<файл>.bak-before-<что-меняем>` — откат тогда сводится к `cp` обратно.

Изменения `.env` подхватываются только пересозданием контейнера:
`docker compose up -d --force-recreate <сервис>`. Простого `restart` мало.

**Добавление пользователя** — синхронизацию делает `./add-user.sh <nick>`,
остальное вручную:

1. `./add-user.sh <nick>` — создаёт базу, волт и `hx-livesync-<nick>`, выдаёт
   passphrase и setup-URI;
2. свой контейнер агента `hermes<n>` с `TELEGRAM_BOT_TOKEN<n>` и
   `TELEGRAM_ALLOWED_USERS<n>` в `.env`, волт `vault-<nick>` примонтировать в
   `/opt/data/vault`;
3. сразу после первого старта агента — `HX=<n> ./switch-model.sh kimi`, иначе
   агент останется на сгенерированном по умолчанию `provider: auto` и будет
   просить у провайдера чужую модель, отвечая пользователю ошибкой.

Проверять работоспособность бота запросом `getUpdates` **нельзя**: запрос
перехватывает сессию у работающего агента и роняет его в backoff. Для проверки
токена годится `getMe`, а работу подтверждает живое сообщение от пользователя.
Бот не может написать первым — пока пользователь не отправил сообщение,
`sendMessage` отвечает `Bad Request: chat not found`.

## Ограничения

- **Только один экземпляр на бота.** Второй запущенный контейнер с тем же
  `TELEGRAM_BOT_TOKEN` будет отбирать слот long-polling, и оба получат
  `409 Conflict: terminated by other getUpdates request`.
- **Вспомогательный клиент.** В логах возможны предупреждения
  `Auxiliary Nous client unavailable`. Это сжатие контекста, суммаризация и
  заголовки сессий — на основной диалог не влияет, настраивается через `hermes auth`.

## Требования

Docker с плагином Compose v2. Проверялось на Docker 29 / Compose v2.40.
